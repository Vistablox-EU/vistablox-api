## Decisions from Damir — round 2 (2026-09-11, same day)

These **replace** the earlier decisions 5 (non-biometric fallback) and 8 (wallet custody) above, and **refine** decisions 6 (holds) and 7 (on-chain broadcast). The rest of round 1 stands unchanged.

1. **Chain confirmed: Base (and Base Sepolia for staging).** No longer an assumption pending confirmation — this plan's earlier "confirm my reading" open question is resolved. *Reflected in: "Wallet architecture" section.*
2. **VistaBlox has zero control over user wallets.** No co-signer (the option-C multisig-style design is explicitly rejected), no recovery guardian or HSM key, no key of any kind on the wallet — only the device owner ever signs. VistaBlox may only *send* payment/signing requests. Where VistaBlox runs a relay (bundler) and a gas sponsor (paymaster), those can refuse service but can never move or block funds on-chain. *Reflected in: "Wallet architecture" section, replacing decision 8.*
3. **Biometrics mandatory, no non-biometric fallback — replaces decision 5 entirely.** `device_credential` as an `auth_class`, its lower caps, the post-signature `scheduled` delay, `DEVICE_CLASS_NOT_PERMITTED`, and the P6/P7 fallback-approval reasoning all go away — they existed only to support a fallback class that no longer exists. Enrolment now accepts `auth_class: "biometric"` only; Android attestation must show biometric-only user auth, iOS relies on App Attest proving the genuine app set `.biometryCurrentSet`. A device with no strong (Class 3) biometric enrolled is blocked outright — budget Android phones with only weak (Class 2) face unlock can't use VistaBlox. The European Accessibility Act most likely doesn't apply yet under the microenterprise exemption; noted to revisit once VistaBlox grows past it, not decided now. *Reflected in: "Biometrics mandatory" section, replacing "Non-biometric fallback policy."*
4. **Wallet: a Safe smart account from day one — replaces decision 8's short-term/long-term split entirely.** No interim wrapped-secp256k1 wallet is built at all; the long-term ERC-4337 direction from round 1 *is* the day-one design. Owners are each enrolled device's biometric P-256 key, verified on-chain via RIP-7212, threshold 1 (any device signs). Recovery is a ZK Email module: a DKIM proof from the user's own mailbox can rotate owners after a 7-day delay, cancellable by any enrolled device; no VistaBlox key is ever in the recovery path, and a relayer can only submit proofs, never forge them. Pairing a device = `addOwner`; removing one = `removeOwner`; account recovery or re-enrolment with no second device to co-sign goes through ZK Email instead. T3 carries `signed_user_op`, not `signed_tx`. A public-bundler fallback exists if VistaBlox is unreachable for 7 days (the user then pays gas in ETH); the server path stays default, with limits and holds applied. The Safe address gets registered in the property token's ERC-3643 identity registry; issuer-side agent-role recovery stays the last resort for tokens specifically. Audit status must be checked and documented for every contract/module used, especially the ZK Email module — this is a concrete deliverable, not just a design note. *Reflected in: "Wallet architecture" section.*
5. **Holds, refined around one user story: "view everything immediately after recovery; move money again after 7 days."** Account-recovery hold becomes **7 days**, matching the ZK Email delay (was 72h). Pairing and re-enrolment stay **24h**, *unless* the wallet-owner rotation itself forces a longer wait — i.e., a single-device user re-enrolling or being paired with no second device to co-sign `addOwner`/`removeOwner` has no choice but to go through the 7-day ZK Email path for that rotation, even though the *auth* side of re-enrolment is otherwise a same-day flow. *Reflected in: Data model and Threat model.*
6. **UX principle: no crypto jargon anywhere the user sees it.** Gas is sponsored, there's no seed phrase, and the message is "your phone is your key" — never "wallet," "signature," "gas," or similar, in user-facing copy (mobile-owned, noted here for backend copy in emails/push where relevant).

## Why (in my own words)

Passkeys solve the wrong problem for us. Their whole value proposition — recoverability via iCloud Keychain / Google Password Manager, so losing a phone doesn't lose your credential — is exactly the property we don't want for a high-risk financial app. The credential's root of trust is the platform account, not the physical device, and a WebAuthn "user verified" flag only ever means "some local unlock happened," which on most devices includes the passcode, not necessarily the biometric. A thief who has watched someone type a passcode passes that check as cleanly as the legitimate user.

The fix is to stop treating the biometric as an authentication factor and start treating it as what it actually is: a *lock on a key*. A non-exportable P-256 key generated inside the Secure Enclave or StrongBox, configured so the OS will only use it after a fresh biometric check, gives us something WebAuthn can't: a credential that is cryptographically provable to exist on one specific piece of hardware, and unusable without both the hardware and the enrolled biometric. Google/Apple sign-in stops being "how you log in" and becomes "how you prove identity once, at enrollment and recovery" — which also means a compromised Google account alone no longer gets an attacker anything on an already-enrolled device.

The same logic extends past login: the 5-minute fresh-auth window we have today is a *time-based* trust decision applied uniformly, when what a transfer actually needs is an *action-specific* one — a signature over the exact request being approved, from the exact device it belongs to, consumed exactly once. That closes the door on a whole class of confused-deputy and replay problems the current design doesn't fully address, and it's the same reasoning that makes recovery codes the wrong tool for account recovery: a code you wrote down is a shared secret with no device binding at all, and a phished Google session plus a screenshotted code is enough to enroll a brand-new passkey today, on any device, with no biometric check ever performed on the account's actual owner. Replacing that with a flow that reproves "you are this device" and "you are this KYC'd person," rather than "you know this string," is the same design principle applied to recovery instead of login.

## Verified findings on the flagged gaps (5a–5g)

Checked against current code before writing anything else, since a plan for a security lead should not repeat unverified claims:

- **5a (recovery-code bypass) — confirmed exploitable as described.** `RedeemAccountRecoveryCodeService.execute({accountId, code})` takes `accountId` straight from the request context, which `requireOAuthBootstrapAuthentication` populates for a merely-*pending* OAuth session (`authenticationLevel: "oauth_pending"`). A valid recovery code plus a completed Google/Apple sign-in — no passkey, no prior device — is sufficient to receive a passkey-registration bootstrap token. Google account takeover (SIM swap, session cookie theft) plus a screenshotted recovery code is a full account takeover with no biometric check anywhere in the chain.
- **5b (TOTP satisfies step-up) — confirmed.** `VerifyTotpService.execute` calls `recordSessionFreshAuth` on **both** the primary TOTP-code branch and the backup-code branch (`totp.service.ts:74-90`). A backup code — a value the user wrote down — is currently exactly as strong as a biometric-confirmed passkey for the purposes of `requireFreshAuthentication`.
- **5c (no step-up on wallet actions) — confirmed.** `wallet.router.ts` gates `POST /` (register), `POST /transfers`, and `GET /` on `requireAuthentication` only; `requireFreshAuthentication` is not in the chain anywhere in the wallet module. Only the offering-reservation flow (`offering.router.ts`) currently uses it.
- **5d (fresh-auth is time-based, not action-bound) — confirmed by design.** `require-fresh-authentication.ts`'s only check is `lastFreshAuthAt >= now - 5min`; nothing ties a confirmation to the specific request it's meant to authorize. A user who steps up once can perform *any* number of different sensitive actions inside that window.
- **5e (DPoP Phase 1 accepts unbound sessions) — confirmed; this is deliberate Phase 1 behavior** (see the DPoP device-binding work earlier this session, #41–#51). The new design's migration section below proposes closing it as part of cutover, matching the brief.
- **5f (SMTP placeholder) — confirmed.** `.env.example` ships `SMTP_HOST=smtp.example.com`, and `better-auth.factory.ts` itself carries a comment acknowledging this is still a placeholder in production. The new recovery flow's email-invite step has a hard dependency on this being fixed before it can ship; Damir's decision 13 additionally requires SPF, DKIM, and DMARC `p=reject` on whatever replaces it, since recovery emails are a phishing template — see Observability.
- **5g (doc/code disagreement) — verified, and the resolution is the opposite of what the doc claims.** `docs/account-recovery.md` states full-lockout recovery sends a link "via better-auth's own `requestPasswordReset`." The actual code (`CompleteAccountRecoveryService` → `BetterAuthCustomerAccountAdministrator.sendRecoveryCompletionEmail`) does not call `requestPasswordReset` anywhere — it calls `issuePasskeyBootstrap`, the same bootstrap-token mechanism every other passkey-replacement flow in this codebase already uses. So `emailAndPassword: { enabled: false }` does not actually break today's recovery flow (the doc's own premise doesn't apply to what the code does) — but the doc itself is stale and should be corrected independently of this redesign. Not fixing it as part of this plan (plan-only), but flagging it so it doesn't get carried into whatever documentation this redesign eventually needs.

## Phases and milestones

Phased the same way DPoP Phase 1 was: land the new capability *alongside* the old one, migrate real users deliberately, then remove the old path. Each phase is independently shippable and independently revertible (nothing in an earlier phase requires a later one to be safe).

**Phase 0 — foundations (backend + mobile in parallel, no user-facing change)**
- Device record data model, challenge service, JWS verification library (purpose-namespaced, reusing the existing DPoP proof verifier's JOSE/ES256 machinery where the shapes overlap — see "Build on what exists").
- Android key-attestation verification (cert chain → Google root, revocation list, biometric-only user-auth check per round 2) and iOS App Attest verification, as standalone, independently testable modules.
- **Mainnet-gate deliverables (Damir's explicit four-part sign-off, no external audit budget)**: (1) confirm zero custom on-chain code; (2) close DevOps's audit-status tracking table's remaining "to verify" cells, especially confirming the ZK Email module's 2 high-severity Ackee findings are fixed in the pinned commit; (3) write the internal review checklist; (4) design and run the Base Sepolia adversarial soak test (see Test strategy). All four before Phase 2 commits to a specific module version or goes anywhere near mainnet — not assumed safe by default.
- Feature-flagged off in production; exercised only in staging/CI.

**Phase 1 — enrollment + login, opt-in**
- `enrol/challenge`, `enrol/verify`, `login/challenge`, `login/verify` endpoints live, but customer passkey login remains the default. A small internal/staff-controlled cohort (or a feature flag per account) can opt into device-key login to validate the full flow against staging with real devices, mirroring how DPoP Phase 1 was validated against a real device before wider rollout.
- Safe deployment wired into first-device enrolment (E2), via the Safe proxy factory — eager, not counterfactual (see "Wallet architecture"); the app verifies the deployed owners/modules with a read-only call, and the backend should too before proposing operations against it.
- DPoP stays exactly as it is today (Phase 1 semantics: bind when present, no hard requirement).

**Phase 2 — transaction signing**
- Propose/view-challenge/sign/execute lifecycle for the two existing money-moving actions (wallet registration/change, wallet transfer), now built as UserOperations against the Safe rather than plain transactions — `RequestWalletTransferService` changes from encoding a plain unsigned tx to proposing a UserOperation. Reservation/offering flows keep `requireFreshAuthentication` unchanged in this phase — folding them in is a separate, later decision, not blocking this rollout.
- Device-hold and new-device-notification logic; `addOwner`/`removeOwner` UserOperation construction for pairing (P3) and revoke (D3), with the async on-chain-status polling from "Contract additions" above.
- Bundler and paymaster integration (which provider is DevOps's call — see Open Questions) — VistaBlox's relay is the default path, with the public-bundler fallback for 7-day unreachability.
- Runs alongside the *existing* fresh-auth window (both active) until the mobile signing UI is confirmed working end-to-end, then the fresh-auth requirement on these two routes is removed in favor of per-action signing only.

**Phase 3 — recovery redesign**
- New KYC-bound recovery flow behind a flag. Old recovery-code flow (`rotate`/`redeem`) stays live in parallel until Phase 3 is validated — recovery is the one flow where "can't get back into your account" is worse than a slower rollout.
- ZK Email wallet-recovery module wired in alongside the KYC recovery flow, both landing on the same 7-day hold — the exact mechanical coordination between the two (see "Wallet architecture") needs settling with mobile-dev before this phase, not during it.
- Requires 5f (real SMTP) resolved before this phase can go to any real users.

**Phase 4 — cutover**
- Customer passkey login disabled; existing passkey users are required to log in with the passkey one last time and enroll a device key in the same session (mirrors DPoP's own cutover pattern).
- Recovery-code endpoints, TOTP backup codes, and the customer-facing passkey plugin paths removed.
- DPoP binding becomes mandatory for all customer sessions (closes 5e for real, not just Phase-1-style).

**Phase 5 — cleanup / evaluate the better-auth question**
- Once the customer passkey plugin is gone, revisit whether customer auth moves out of better-auth into its own module (see "better-auth vs. own module" below). Not gated on anything upstream; purely an internal-quality decision that can happen whenever there's a good window for it.

## 3. Shared wire contract (identical in both plans)

> Agreed between vistablox-auth-dev and vistablox-mobile-dev, updated with both of Damir's decision rounds of 2026-09-11. Changes need both owners.

### 3.1 Conventions

- **Host:** `https://api.vistablox.io`. Every endpoint is under `/v1`. JSON bodies. Success bodies are `{ "data": { ... } }`; `202`/`204` as noted.
- **Every request** carries a DPoP proof (the existing contract), plus `Authorization: Bearer <token>` whenever the client holds a session. The client never sends cookies.
- **Session delivery:** every response that creates, upgrades or rotates a session sets `set-auth-token`. Enrolment and recovery ROTATE the token. The body includes `session_expires_at` and `authentication_level`.
- **Errors:** `application/problem+json` `{ type, title, status, detail, code, trace_id }`, plus extension members where noted (`retry_after_s`, `hold_until`, `limit_kind`, `resets_at`, `reason`). `code` is authoritative, and each code has exactly one meaning. The backend implements device auth as a better-auth plugin; the paths, shapes and envelope here hold regardless.
- **Customer-only:** staff and partner accounts can't create any session in the app. Google/Apple sign-in and every session-creating endpoint answer with the existing `STAFF_PASSKEY_REQUIRED`. RC1 treats a staff email as unknown (still `202`).
- **Wallet boundary:** each customer's wallet is a Safe smart account on Base (Base Sepolia on staging). Its only owners are the biometric keys of the customer's enrolled devices (threshold 1, at most 2 owners). VistaBlox holds **no key of any kind** over it: the server proposes user operations and relays what a device signed. It never signs. The server obtains gas sponsorship (Coinbase CDP) and submits every user operation; the app holds no bundler or paymaster key.
- **Encodings:** base64url without padding everywhere. Times are RFC 3339 UTC. The server's `Date` header is the client's clock reference.
- **Identifiers:**
  - `dpop_jkt`: RFC 7638 thumbprint of the DPoP key.
  - `bio_jkt`: thumbprint of the biometric key.
  - `device_id`: opaque, server-assigned.
  - `owner_address`: the device's Safe owner address, which **the client computes itself**. For the account's first device, it's Safe's `SafeWebAuthnSharedSigner`, a singleton configured per Safe with that device's key. For every later device, it's the device's own `SafeWebAuthnSignerProxy`, derived from its biometric public key through `SafeWebAuthnSignerFactory`.
  - `safe_address`: the customer's account.
  - `app_attest_key_id`: iOS only.
- **Device resolution:** the server resolves the device record from the request's DPoP `jkt`. Any `device_id` in a body, claim or assertion must match it.
- **Binding value:** `binding = SHA-256(ASCII(challenge + "." + bio_jkt))`. It's used for Android `requestHash` (b64url) and iOS `clientDataHash` (raw).

### 3.2 Device-auth JWS (off-chain actions)

Used for `enrol-device`, `login`, and `tx` requests that have no on-chain part.

- **Compact JWS:** header `{ "alg": "ES256", "typ": "vistablox-device-auth+jwt", "kid": "<bio_jkt>" }`. Only `enrol-device` adds `"jwk"` (public P-256). The signature is raw `r‖s`.
- **Common claims:** `purpose`, `challenge` (server-issued, single-use), `iat` (±60s), `device_id` (except the first enrolment of a new device).

| `purpose` | Extra claims |
|---|---|
| `enrol-device` | `dpop_jkt` (must equal the request's proof jkt); `device_id` only when re-enrolling an existing device record |
| `login` | none |
| `tx` (off-chain types only) | `request_id`, `request_type`, `amount_minor` (decimal string), `currency`, `destination` (`{ kind: "wallet"\|"iban"\|"contract", value }`), `created_by` (`{ kind: "user"\|"platform"\|"staff", label }`), `created_at`, `expires_at`. Compared field by field, as exact strings; any difference is `TX_FIELD_MISMATCH`. |

- **Rules:** each purpose has its own challenge namespace; challenges are consumed atomically; `kid` must equal the stored `bio_jkt`.

### 3.3 Owner assertion (on-chain actions)

Every action that changes the Safe is approved with **one** biometric signature. That covers a transfer or investment, adding, replacing or removing an owner, cancelling an email recovery and, for the first device, deploying the Safe at enrolment. The one signature is both the on-chain owner signature and the server's proof of approval. That's needed because an Android per-use key authorizes exactly one signature per biometric prompt.

- **`op_hash`:** the app decodes the proposed user operation itself (section 4.6) and computes `op_hash`, the Safe4337Module operation hash (EIP-712 `SafeOp`), from its own decode. It is never taken from the server.
- **The app builds a WebAuthn-shaped assertion with its own key** (no passkey API):
  - `authenticator_data` = `SHA-256("api.vistablox.io") ‖ 0x05 (UP|UV) ‖ 0x00000000`.
  - `client_data_json` = `{"type":"webauthn.get","challenge":"<b64url(op_hash)>","origin":"https://api.vistablox.io","vb_purpose":"<purpose>","vb_challenge":"<server challenge>","vb_device_id":"<device_id>"}`. Everything after `challenge` is the `clientDataFields` string that Safe's WebAuthn verifier appends unchanged.
  - `signature` = ES256 over `authenticator_data ‖ SHA-256(client_data_json)`, as raw `r‖s`, **normalised to low-s**.
- **Purposes:** `tx`, `approve-new-device`, `manage-device`, `cancel-recovery`, and `enrol-device` for the first device only (over E1b's deployment operation). Each has its own challenge namespace.
- **The server checks:**
  - `vb_challenge` is its own single-use challenge for this purpose and target;
  - `vb_device_id` matches the request's DPoP jkt;
  - the signature verifies against that device's stored key;
  - `op_hash` equals the hash of the user operation it proposed.

  Then it encodes Safe's contract signature (`v = 0`, wrapping `authenticator_data`, `clientDataFields`, `r`, `s` for the device's owner, which is the shared signer or its proxy) and submits the user operation to the bundler.
- **On-chain:** the first device verifies through `SafeWebAuthnSharedSigner`, and later devices through their own `SafeWebAuthnSignerProxy` (from `SafeWebAuthnSignerFactory`). Both verify with the RIP-7212 P-256 precompile on Base, with the FCL verifier as fallback. The Safe checks the challenge and the flags, not the origin. The UV flag and the origin are asserted by the app; the real assurance is the hardware biometric gate on the key, plus attestation.

### 3.4 Attestation blobs

These are sent on `enrol/verify`, on `login/verify` when `attestation_required` is true, and on every signing action (T3, D3, P3, ER5). For signing, Android sends an `integrity_token` and iOS an App Attest `assertion`, with `binding` built from that action's challenge.

- **Integrity levels (Android, production):** login needs `MEETS_DEVICE_INTEGRITY`. Actions that move money or add a phone (T3, P3) need `MEETS_STRONG_INTEGRITY`; otherwise `STRONG_INTEGRITY_REQUIRED`. Defensive actions (D3 removing a phone, ER5 cancelling a recovery) need only device integrity, so a customer on an older phone can always stop an attack. Staging records the strong verdict but doesn't enforce it.

- **Android:** `{ "platform": "android", "key_attestation_chain": ["<b64 DER leaf>", "..."], "integrity_token": "..." }`.
  - The biometric key is generated **after** the challenge is fetched, with `setAttestationChallenge(ASCII(challenge))`.
  - `requestHash` = b64url(`binding`).
  - The attestation must show a **biometric-only** key (`userAuthType` biometric, with no device credential), or the server answers `ATTESTATION_INVALID`.
  - `integrity_token` is omitted while no Play Integrity cloud project exists. Staging then runs `PLAY_INTEGRITY_POLICY=disabled`, which production refuses. Key attestation is always required.
- **iOS:** `{ "platform": "ios", "app_attest_key_id": "...", "attestation_object": "<b64>" | "assertion": "<b64>" }`.
  - `attestation_object` is sent at the first enrolment of an install (`attestKey(keyId, binding)`); `assertion` after that.
  - The App Attest key is a third key, separate from both Secure Enclave keys.
  - Secure Enclave access-control flags aren't attested; App Attest proves that a genuine app set them.
- **No Google Play services:** there's no integrity token, so the server answers `DEVICE_UNSUPPORTED`. The app blocks such devices at launch anyway.

### 3.5 Endpoints

"Pending session" means a DPoP-bound session of level `oauth_pending` (a fresh Google/Apple sign-in; during migration also a legacy `oauth_passkey` session). Every endpoint requires a DPoP proof. Endpoints whose auth is "none" ignore an `Authorization` header if one is present: a stale token is never a reason to fail.

## Data model / storage changes

New tables (`auth` Postgres schema, following the existing DPoP-replay-table precedent of new infrastructure going in `auth` properly rather than wherever convenient), field names matching the contract's endpoint responses directly (D1, E2, ER2, etc.):

- **`auth.devices`**: `device_id` (pk), `account_id`, `dpop_jkt` (unique, the currently-bound session key), `bio_jkt` (the `kid`), `biometric_public_jwk`, `owner_address` (server-computed and verified, never trusted from the client's own claim — for the account's **first** device this is the `SafeWebAuthnSharedSigner` singleton's address, not a per-device proxy; for every later device it's that device's own `SafeWebAuthnSignerProxy` address, per Damir's r7 deployment decision — see "Wallet architecture"), `platform` (`ios`/`android`), `model`, `os_version`, `app_version`, `attestation_metadata` (jsonb — cert chain reference / App Attest key id, not the raw blobs long-term), `status` (`active`/`active_hold`/`pending_approval`/`revoked`), `owner_status` (`owner`/`pending`/`none` — backs `D1`; `pending` while an `addOwnerWithThreshold`/`swapOwner`/deployment UserOperation is submitted but not yet included), `hold_until` (nullable — only ever set by an email-recovery hold; pairing and re-adds carry no hold, decided), `created_at`, `last_seen_at`, `push_token` (nullable). No `auth_class` column: biometric-only, no fallback class. No `push_provider` column: FCM HTTP v1 only for both platforms, `platform` already tells the backend what it needs.
- **`auth.device_challenges`**: `purpose`, `challenge_id` (the two together, pk), `device_id` (nullable — `enrol-device`/pairing challenges can precede a device record), `dpop_jkt`, `expires_at`, `consumed_at` (nullable). Same `INSERT ... ON CONFLICT DO NOTHING` single-use pattern as `dpop_replays`, same hourly prune job pattern in `worker.ts`. Covers both the plain-JWS challenges (3.2) and the owner-assertion challenges (3.3) — same table, same atomicity requirement, `purpose` already namespaces them.
- **`auth.device_pairings`**: backs P1–P5 — `pairing_id`, `code` (6-digit), `account_id`, `new_device_id` (fk into `auth.devices`, created `pending_approval`), `replaces_owner_address` (nullable — set when this pairing is a device re-adding itself via `swapOwner`, not a fresh `addOwnerWithThreshold`), `status` (`pending`/`pending_onchain`/`active`/`rejected`/`expired`), `owner_change_id` (fk into `auth.wallet_owner_changes`, set once `P3` submits the owner-assertion-authorized operation), `expires_at`. P6/P7 and `approval_methods` from earlier drafts are gone — settled, not part of section 3.
- **`auth.wallets`**: one row per account — `account_id` (pk), `safe_address`, `chain_id`, `deployed_at`, `created_at`. **Deployed eagerly at the first device's enrolment** (via the Safe proxy factory, initializer carrying the owner/threshold/`Safe4337Module`/email-recovery-module configuration) — not counterfactual/lazy, correcting an earlier draft of this plan. No `status` column needed since there's no `predicted`-but-undeployed state to track anymore.
- **`auth.wallet_owner_changes`**: tracks every on-chain owner-set change so pairing/revoke/re-enrolment can report `pending_onchain` status truthfully instead of pretending an on-chain confirmation is instant — `owner_change_id`, `account_id`, `type` (`add`/`swap`/`remove`), `target_owner_address`, `initiated_by` (`device_id`), `user_op_hash` (nullable until submitted), `status` (`pending`/`submitted`/`included`/`failed`), `created_at`, `included_at`.
- **`auth.email_recovery_requests`**: backs `ER1`–`ER5` — `request_id`, `account_id`, `new_owner_address`, `initiated_by_device_id` (the recovery-pending/re-enrol session's device), `status` (`awaiting_email`/`pending`/`executable`/`executed`/`cancelled`/`expired`), `executable_at` (nullable, set once the module's on-chain delay starts — this **is** `D1`'s `hold_until` and `RC3`'s `hold_until` for the account, not a separate concept), `created_at`. One outstanding request per account at a time — a second `ER1` while one is `pending`/`executable` returns `EMAIL_RECOVERY_PENDING` rather than creating a second row.
- **`auth.recovery_cases`**: backs `RC1`–`RC3` (down from `RC1`–`RC5` — the old-device kill-switch moved to `ER4`/`ER5`, since cancelling wallet recovery is now a wallet-side owner-assertion action, not an account-side one) — `case_id`, `account_id`, `dpop_jkt` (enforces `RECOVERY_WRONG_DEVICE`), `didit_session_id` (nullable until `RC2`), `consent_version` (nullable until captured, required before `didit_session_id` can be set), `status` (`awaiting_kyc`/`in_review`/`manual_review`/`approved`/`rejected`/`cancelled`/`expired`), `created_at`, `resolved_at`. `RC2`'s session is a distinct **recovery-pending** level, accepted only by `E1`/`E2` and `ER1`/`ER2` — narrower than the existing `oauth_pending` level, needs its own `authenticationLevel` value in `session-resolver.ts`'s existing enum, not a reuse of `oauth_pending`.
- **`auth.reenrol_selfies`**: backs `RE1`–`RE2` — `selfie_id`, `device_id` (the re-enrolling device), `didit_session_id`, `consent_version`, `status` (`awaiting_kyc`/`in_review`/`approved`/`rejected`), `created_at`. `RE2`'s `next_step` (`device_approval`/`email_recovery`) is computed live from whether the account has another active device — not stored.
- **`auth.signing_requests`** (or extend whatever table `RequestWalletTransferService` already writes to, if one exists by the time this ships) — backs `T1`–`T3`: `request_id`, `account_id`, `device_id`, `request_type`, `amount_minor`, `currency`, `destination` (jsonb — `{kind, value, display_name}`), `created_by` (jsonb — `{kind, label}`), `on_chain` (bool — **off-chain request types still exist**, correcting an earlier draft of this plan; `T3` branches `{challenge, assertion}` for on-chain vs `{challenge, jws}` for off-chain), `user_op` (jsonb, nullable — the proposed UserOperation, on-chain types only), `status` (`pending`/`signed`/`submitted`/`included`/`expired`/`cancelled`), `challenge_id` (fk into `device_challenges`), `signed_user_op` (jsonb, nullable, on-chain types — the client-signed operation the server relays through its bundler; off-chain types instead record the plain JWS), `user_op_hash` (nullable until submitted), `created_at`, `signed_at`, `expires_at`. Device revocation (D3) and recovery starting must both cancel a device's `pending`/`signed` requests.
- **`identity` schema addition**: a `document_identity_hmac` column on the KYC record (HMAC of document number + issuing country + DOB, keyed the same way other identifier-hashing in this codebase already is — see `better-auth-audit.plugin.ts`'s `identifierHashKey` pattern) — the "same-document check" the recovery flow's (RC2/RC3) and re-enrolment flow's (RE1) face-match are both paired with.
- **`identity`/`platform` schema addition — guardian/email backup**: backs `W1`/`W2` — a `guardian_email`, `email_backup_status` (`not_set`/`awaiting_acceptance`/`active`), and the acceptance-command state, most naturally living alongside the existing wallet/investor-profile read model this extends (`/v1/investor-profile/wallet`) rather than in `auth` — it's account/investor data, not an auth primitive.

**`GET /v1/app/config` (C1)**: not a table — a small config service reading feature-flag state (`device_auth`, `device_enrolment_required`, `passkey_login`, `signing_requests`, `recovery_v2`) and `min_app_version` per platform. Backed by the same environment-driven flag pattern as `RESERVATION_FUNDING_RAIL_ENABLED`/`OPERATING_DISTRIBUTION_ENABLED` for the booleans; `min_app_version` needs an operator-settable value (not just an env var, since it changes on every mobile release without a backend deploy) — simplest is a small `platform.app_config` row DevOps can update directly, matching how other operator-tunable-without-a-deploy settings are handled elsewhere in `platform`.

Removed (Phase 4 / cutover): `account_recovery_codes` table and its repository/service pair, TOTP backup-code storage on `mfa_backup_codes`, and whatever the customer passkey plugin's own tables hold once that plugin is removed from the factory.

## Migration and cutover

Follows the DPoP precedent exactly, since that rollout is the one piece of prior art in this codebase for "replace an auth primitive without breaking everyone logged in":

1. Phase 1–3 ship behind the `device_auth`/`recovery_v2` flags served by `GET /v1/app/config` (C1), validated on staging with real devices the same way DPoP was (a session-creation bind, then a live device test, watched via logs before wider rollout).
2. `device_enrolment_required` (also served by C1) turns on once enrollment and login are validated: every existing passkey user is prompted to enroll a device key on their next launch, completing one last passkey login in the same session (same "one last passkey login, enroll the replacement in the same flow" pattern DPoP used for session binding). Passkey login itself stays available throughout this step.
3. A cutover date is set once Phase 3's recovery flow is validated end-to-end (recovery is the one path where a bug locks someone out permanently, so it gets the most real-device testing before cutover, not the least).
4. At cutover: `passkey_login` flips off and `min_app_version` is raised (both via C1) so any client too old to have the enrollment prompt is blocked outright rather than hitting a removed endpoint; customer passkey, recovery-code, and TOTP-backup-code endpoints are removed server-side; DPoP binding is made mandatory (Phase 1's `phase1CutoverAt`-style permissiveness goes away for customers). A user who never updated and never enrolled reaches this point only through the forced-update gate, then re-enters through mobile-dev's recovery flow (RC1–RC3, plus email recovery on the wallet side) on their next successful login, exactly like any other lost-credential case — no separate "missed migration" code path needed.
5. Staff auth (better-auth, WebAuthn, `WEBAUTHN_RP_ID`) is untouched by any of this — separate population, separate plan section below.

## Staff scope: exclusion from device auth, and staff login (decided)

**Decided by Damir: the mobile app and every device-auth endpoint are customer-only.** Verified against current code rather than assumed: `src/modules/auth/infrastructure/better-auth-staff-account-guard.plugin.ts` already runs a `session.create.before` hook that throws `STAFF_PASSKEY_REQUIRED` whenever a `staff_partner`-population user's session is created through anything other than the staff passkey path. Since this plan's device-key session creation (E2, L2, and the RE-/RC-scoped rotations) routes through the same `internalAdapter.createSession` mechanism as passkey does (see "Build on what exists"), a `staff_partner` account is already rejected the moment it tries to obtain a device-auth session — no new code needed for E1/E2/L1/L2/D*/RE*/P*/T*, this is inherited for free from existing infrastructure.

**One real gap**: `RC1` (`POST /v1/auth/recovery/start`) resolves an account by email *before* any session exists, bypassing the session-creation guard entirely. Without a check, a `staff_partner` email submitted there would create a real `auth.recovery_cases` row and let a staff account's credentials be replaced by a customer-style device-recovery flow it was never meant to use. Fix: `RC1`'s account lookup treats a `staff_partner` match the same as "account doesn't exist" — still returns the generic `202`, creates no case — preserving the existing anti-enumeration behavior with no new error code or contract change needed.

No new endpoint-facing error code is needed for staff exclusion: the existing `STAFF_PASSKEY_REQUIRED` (from the guard above) already covers the case. **Correction from mobile-dev, now reflected here**: this *is* reachable from the app in practice, not just defense-in-depth — a staff member who installs the customer app and taps "Continue with Google" hits it at sign-in, before any device-auth endpoint is ever called. Mobile-dev is adding it to their section 3.5 with client behavior: a "This account can't use the VistaBlox app" screen, drop the token, no retry.

**Staff web login stays on passkeys** via `@better-auth/passkey`, the path staff already use today: the staff guard above only admits `/passkey/verify-authentication` and `/passkey/verify-registration`. An earlier version of this plan moved staff to FIDO2 hardware security keys with attestation and an AAGUID allowlist. Damir dropped that on 2026-09-11, because VistaBlox has no FIDO hardware keys, and it isn't deferred to later. This plan builds nothing on the staff side.

## better-auth vs. own module (decided: plugin now, revisit after cutover)

**Decided by Damir: keep better-auth, add device-key auth as a plugin now; revisit the standalone-module option only after Phase 4's cutover.** The new challenge/enroll/verify endpoints create sessions via `internalAdapter.createSession`, the same mechanism `@better-auth/passkey` itself already uses (verified against `@better-auth/passkey`'s source during the DPoP work this session — `internalAdapter.createSession` unconditionally routes through `databaseHooks.session.create.before`, which is exactly where DPoP binding and this plan's device binding would both need to hook in). Session storage, revocation, the audit plugin, and the session mirror all keep working unmodified. One session system serves both populations, which matters given staff/customer account-mapping logic already lives on top of the shared `auth_session` table.

**Confirmed to mobile-dev: this does not move the public HTTP surface to `/api/auth` or `{code, message}`.** "Plugin" here describes the *implementation mechanism* for session lifecycle (creation hooks, DPoP-style binding), not the public routing. Every existing customer-facing precedent in this codebase already separates the two: DPoP itself is wired as a `databaseHooks.session.create` hook inside a better-auth plugin, yet `POST /v1/auth/sessions/devices/:jkt/revoke` (its customer-facing endpoint) is an ordinary `/v1` Express route in `customer-session.router.ts` that calls into better-auth's `auth.api.*`/`internalAdapter` internally — never a `/api/auth/*` route. Every device-auth endpoint in section 3.4 (E1/E2/L1/L2/D*/RE*/P*/T*/RC*) follows that same shape: a new `/v1` Express router (`requireAuthentication`-gated where a session already exists, unauthenticated-but-DPoP-checked where one doesn't), `AppError`/`errorHandler` producing `application/problem+json`, and the handlers call the better-auth plugin's session-creation/rotation/revocation internals rather than being better-auth endpoints themselves. Section 3.4's paths and 3.1's envelope stay exactly as written — no change needed on mobile's side for this.

**Trade-off worth naming honestly**: the brief's own complaint (item 4) is that "bending a web-cookie framework to fit native apps" is exactly what produced the bearer/passkey-challenge cookie-merge bug found and fixed this session (#48) — real complexity in the security-critical path, from a genuine architectural mismatch, not a one-off bug. A plugin approach inherits that mismatch again for device-key auth specifically, since it's registering more `before`/`after` hooks into the same `runBeforeHooks` merge mechanism that bug lived in. The dispatch-level regression test added this session (#49) exists specifically because that merge behavior is subtle enough to break silently — a new plugin adds another hook to reason about there, though not a new *failure mode*, since the merge behavior itself doesn't change, and this new plugin uses `device_id`-keyed lookups rather than injecting anything into `Cookie`, which was specifically what the earlier bug was about.

**Later option (brief's item 5, once customer passkeys are fully gone)**: move customer auth to a small module VistaBlox owns outside better-auth — Google/Apple ID-token verification (already just `jose`), device-key signature verification (this plan's own JWS verifier), and opaque session tokens stored hashed and bound to DPoP. Better-auth would then only serve staff web login. This removes the cookie-framework mismatch at the root instead of managing around it, at the cost of re-implementing session issuance/revocation/expiry that better-auth currently gives for free. Recommend revisiting this **after** Phase 4 (customer passkeys fully removed), not before — building the new module while passkeys still exist means running two auth systems in parallel for longer, not shorter.

## Biometrics mandatory — no non-biometric fallback (replaces "Non-biometric fallback policy")

**Round-2 decision, superseding round 1's approved fallback shape entirely.** `device_credential` as an `auth_class` is removed, along with everything that existed only to support it: the lower signing caps, the post-signature `scheduled`/`executes_at` delay mechanism, the `DEVICE_CLASS_NOT_PERMITTED` error code, `destination.first_party`, and the "old device can't approve, route to a KYC-selfie alternative" reasoning. `enrol-device` now accepts `auth_class: "biometric"` only.

- **Android**: the key-attestation extension must show biometric-only user authentication (not `AUTH_BIOMETRIC_STRONG | AUTH_DEVICE_CREDENTIAL`) — enrolment rejects a device whose available authenticator is only a device-credential-capable one.
- **iOS**: no independent server-side verification is possible (Secure Enclave access-control flags aren't attested, same asymmetry noted throughout this plan) — this rests on App Attest proving the genuine, unmodified app set `.biometryCurrentSet` rather than `.userPresence`.
- **A device with no strong (Class 3) biometric enrolled is blocked outright.** Accepted consequence, stated plainly by Damir: budget Android phones with only weak (Class 2) face unlock can't use VistaBlox. This is a real accessibility trade-off, not an oversight — the European Accessibility Act most likely doesn't apply yet under VistaBlox's microenterprise exemption, noted here to revisit once the company grows past that exemption, not decided now.

**P6/P7 (the KYC-selfie pairing alternative) has no remaining justification** — their only purpose was letting an account whose sole device was `device_credential`-class add a second device without a biometric approver. With that class gone, every account's existing device is always biometric-capable of approving via P2/P3 directly. Proposing to `vistablox-mobile-dev` that P6/P7 be removed from section 3 entirely, unless they see a case this plan hasn't accounted for — see "Contract additions" below.

## Wallet architecture: Safe smart account, day one (decided and settled — section 3.1/3.3)

**Round-2 decision, replacing round 1's short-term-wrap/long-term-evaluate split outright.** There is no interim wrapped-secp256k1 wallet to build — the ERC-4337 direction round 1 treated as a future evaluation *is* the day-one design, and section 3 v3 (settled with mobile-dev) is now the authoritative shape of it. Chain is confirmed (not assumed) as Base / Base Sepolia via `CHAIN_NETWORK`'s existing schema.

**Custody principle, stated as plainly as Damir stated it**: VistaBlox has zero control over user wallets. No co-signer, no recovery guardian or HSM key, no VistaBlox key of any kind on the wallet — only the device owner ever signs (section 3.1: "VistaBlox holds no key of any kind over it: the server proposes user operations and relays what a device signed. It never signs."). Wherever VistaBlox runs infrastructure that touches a transaction before it lands on-chain (the bundler, the paymaster), that infrastructure can *refuse service* but can never move or block funds.

**Account structure**:
- A Safe smart account on Base (Base Sepolia on staging), ERC-4337, threshold 1, **at most 2 owners** (matching the 2-device limit). **EntryPoint pinned at v0.7 across every component** (bundler, paymaster, SDK) — `Safe4337Module v0.3.0` targets v0.7 and needs Safe ≥1.4.1; nothing mixes in v0.8 until every component has been separately re-verified.
- **Owners**: each enrolled device's biometric P-256 key, wrapped in a `SafeWebAuthnSignerProxy` (from `SafeWebAuthnSignerFactory`) verified via RIP-7212 (address `0x100` on Base since Fjord; ~3,450 gas, ~6,900 after Azul) with the FCL library as fallback. `owner_address` is derived from the public key through the signer factory — the client computes it itself (section 3.1), and the backend independently re-derives the same address server-side before ever using it in a proposed operation, rather than trusting the client's claim.
- **Deploy nothing custom on-chain** (DevOps's principle, followed throughout): canonical `Safe v1.4.1`, `Safe4337Module v0.3.0`, the **Safe passkey signer**, and `zkemail/email-recovery`'s `SafeEmailRecoveryModule` (native — **no `Safe7579` adapter, decided by Damir directly (r7)**, confirming the earlier correction to this plan — the email-recovery module attaches to the Safe without it, and nothing else in this design needs an ERC-7579 module). A pinned per-network contract-address registry (`docs/chain-addresses.md` plus `SAFE_*` config) is checked in CI against each artifact's `extcodehash`. The `Safe7579` Launchpad CRITICAL front-run-takeover finding (Ackee, July 2024) stays a documented caution for if a 7579 module is ever added later — not a live risk in the current design.
- **Deployment mechanism — decided by Damir (r7): option (a), a sponsored UserOperation with `initCode`, signed by the enrolling device. No VistaBlox deployer key ever exists**, which is what makes this compatible with "VistaBlox holds no key of any kind" — the earlier-drafted alternative (a direct factory call needing a `SAFE_DEPLOYER_KEY` and an ETH float) is rejected outright. This has real consequences for the first device specifically, since ERC-7562 forbids calling undeployed code during UserOperation validation — device 1's own per-device signer proxy can't validate its own deploying operation, because it doesn't exist on-chain yet at that point:
  - **Device 1's owner is Safe's `SafeWebAuthnSharedSigner`** (a singleton, configured with the device's P-256 key via `delegatecall` in the Safe's `setup`) — not a per-device proxy. `owner_address` for device 1 specifically is the shared-signer address; every later device still gets its own `SafeWebAuthnSignerProxy` as originally designed.
  - **Enrolment stays one biometric prompt**, settled as `E1`/`E1b`/`E2`: `E1` returns `first_device: bool` so the client knows up front which path to take, no error round-trip. `E1b` (first device only) takes the raw public key — **no attestation at this step** — and returns the proposed deployment UserOperation (CDP `paymasterAndData` already filled in) with **no server-computed `op_hash`**: the client always computes its own from its own decode, deliberately, so a server-supplied hash can never be blindly trusted or invite a shortcut implementation that skips the real check. `E2` then carries both the attestation *and* the owner-assertion together (`vb_purpose: "enrol-device"`, `vb_challenge` equal to `E1`'s challenge) — one verification point, nothing ever sponsored or submitted before that single attestation check passes.
  - **Later devices** (pairing, re-adds) batch `createSigner(x, y)` (deploying that device's own proxy) with `addOwnerWithThreshold`/`swapOwner` via `MultiSendCallOnly`, in the execution phase — no validation-phase ordering problem there, since by execution time the Safe itself already exists.
  - **Re-adding device 1** after a biometric change deploys a fresh per-device proxy (`createSigner`) and `swapOwner`s it in place of the shared signer — device 1 stops being special after its first re-enrolment.
  - The app independently recomputes the expected Safe address and reads the deployed owners/modules back via a read-only call before treating the account as ready (mobile's section 4.5); the backend performs the equivalent server-side check before ever proposing a further operation against that Safe.
- **Authorization mechanism — one WebAuthn-shaped assertion per on-chain action, settled as section 3.3** ("Owner assertion"): covers `tx` (on-chain types), `approve-new-device`, `manage-device`, and `cancel-recovery`. The device signs `authenticatorData ‖ SHA-256(clientDataJSON)`, where `clientDataJSON.challenge` carries the `SafeOp` hash (`op_hash`, computed by the app from its own decode) and VistaBlox's own `vb_purpose`/`vb_challenge`/`vb_device_id` fields ride along as `clientDataFields`, passed through unchanged by Safe's verifier. One signature serves both roles — on-chain authorization and backend request-matching — avoiding a second biometric prompt. Off-chain request types (investments/reservations that don't touch the Safe) still use the plain compact-JWS format from section 3.2; **not every signing request is on-chain**, correcting an earlier draft of this plan that assumed otherwise. **Backend verification, concretely**: check `vb_challenge` against the single-use challenge issued for that purpose/target, `vb_device_id` against the request's DPoP jkt, the signature against the stored key, and `op_hash` against the hash of the operation the backend itself proposed — only then encode the Safe contract signature (`v=0` wrapping `authenticatorData`/`clientDataFields`/`r`/`s`) and submit to the bundler. **Threat-model note**: the on-chain verifier checks the challenge and flags, not `origin` — origin correctness rests entirely on the app being genuine (App Attest/Play Integrity), not on-chain enforcement.
- **Pairing a device = `addOwnerWithThreshold`; a device re-adding itself after a biometric change = `swapOwner`.** Both signed by the approving device's owner-assertion, submitted through a **single configured bundler provider** (`BUNDLER_URL` — one provider, no secondary, per Damir directly, correcting an earlier DevOps recommendation of primary-plus-secondary). **Removing a device (D3) = `removeOwner`**; removing the account's last owner is rejected outright (`LAST_OWNER`, section 3.6) — the account must never end up with zero owners.
- **Holds after pairing/re-add — an open disagreement, not silently resolved either way.** Section 3.7 currently states no waiting period after pairing or a two-device re-add (mobile's proposal, in service of Damir's "one simple story" framing), with only the post-email-recovery 7-day wait remaining. This plan's earlier draft proposed keeping a 24h hold on newly-paired devices specifically, since a hold constrains exactly the device an attacker would have just gotten approved via relay-phishing, independent of the existing-device threshold-1 point. Both positions are recorded as still-open with Damir (see "Open questions"), and section 3 is not being blocked on resolving it — it ships with mobile's proposed default, explicitly flagged as unsettled.
- **Recovery — `SafeEmailRecoveryModule`, settled**: a DKIM proof from the customer's own registered mailbox (confirmed once at onboarding via `W2`) rotates owners after a 7-day delay; any enrolled device can cancel during that window (`ER4`/`ER5`, owner-assertion purpose `cancel-recovery`) — a stale attempt can also be cleared by anyone via the module's permissionless `cancelExpiredRecovery`. The relayer (`recovery@vistablox.io`) runs directly on the existing Coolify mail server — **no smarthost, per Damir directly**: the API submits outbound mail to it (587, STARTTLS, a dedicated account), and it DKIM-signs (selector `mail`) and delivers itself; the relayer only ever *submits* a proof, never forges one, and holds no key. **Still genuinely open, tracked by DevOps**: whether a different relayer could process the same recovery request — this is what actually decides how strong the "VistaBlox unreachable" story is for email recovery specifically (the app-side public-bundler fallback covers on-chain *submission* unreachability; a single-relayer dependency would still leave email recovery itself single-point-of-failure on VistaBlox even if the bundler fallback works). **External trust dependency**: the DKIM registry (`UserOverrideableDKIMRegistry`) the module checks proofs against. **At `executable_at`, the same ERC-7562 constraint that shaped device-1's deployment applies again**: the new phone's owner (its own `SafeWebAuthnSignerProxy`) isn't deployed yet, and there's no other owner left to batch a `createSigner` call with the rotation (that's the whole point of recovery — no other owner exists). The relayer's own completion call handles this by deploying the new phone's signer proxy first via `SafeWebAuthnSignerFactory`'s **permissionless** `createSigner`, then completing the rotation — the relayer already pays gas for the proof submission and gains no additional power over the Safe by also triggering this deployment, since `createSigner` is callable by anyone for any correctly-formed key.
- **"One sitting" recovery, settled as designed by mobile-dev**: `RC2` issues a recovery-pending session accepted only by `E1`/`E2` and `ER1`/`ER2` — the app enrols the new device's key and prepares the recovery command email in the same sitting, the user taps Send once, and full account viewing still waits on separate KYC approval (`RC3`). A pure "reply to our email" one-tap flow was deliberately rejected: it isn't device-bound, so a phished reply alone could add an attacker's device.
- **KYC no longer protects the wallet on its own, stated plainly**: with zero VistaBlox control, the on-chain owner rotation completes after 7 days regardless of the KYC case's outcome; only a device-side cancel actually stops it. KYC still gates *auth*-side account access, not wallet ownership.
- **Fallback path**: if VistaBlox's bundler is unreachable for 7 days, the app may submit directly to a public bundler (Pimlico/Candide public endpoints plus a user-configurable URL), with the customer paying gas from the account's own ~€2–5 ETH reserve (decided — see "Configuration and secrets"). The backend-mediated path stays default, with its request-matching/limits/holds layer intact; the fallback bypasses *VistaBlox's* checks by design, not the Safe's own threshold-1 authorization, and carries no on-chain limit of its own either (decided — see below).
- **Paymaster — decided directly by Damir: option A, VistaBlox sponsors gas, via Coinbase CDP** (bundler and paymaster in one provider; CDP was the provider option A was presented against, Damir can still override that specific choice later). VistaBlox holds no paymaster signing key — CDP's own policy engine decides what gets sponsored, and an ERC-20 paymaster is ruled out outright (a token allowance is itself a spend path). **Sponsored**: Safe creation (`initCode`), calls to allowlisted platform contracts/selectors only (escrow, property token, other platform contracts), owner add/remove, recovery-module configuration, and `cancelRecovery()` always, uncapped — everything else follows the self-paid path. **Caps**: a per-user daily limit (illustratively ~20 ops/day) and a global monthly cap, with mainnet values derived from measured Base Sepolia gas and approved by Damir; alerts fire at 50/80/100% of the cap plus on per-user or refusal-rate spikes. **The CDP allowlist is generated from the same pinned `SAFE_*`/address registry** backing the extcodehash CI check above — one source of truth, so the policy and the pinned addresses can't drift apart. **Key-handling — settled**: the backend proxy, not a client-side CDP key. Since the server already relays every owner-assertion-authorized UserOperation (`T3`/`D3`/`P3`/`ER5`), the app never talks to CDP at all — `BUNDLER_URL` (and `PAYMASTER_URL`) are server-only config, matching section 3.1's addition: "The server obtains gas sponsorship (Coinbase CDP) and submits every user operation; the app holds no bundler or paymaster key." No separate client-restriction question to resolve. `user_op` objects returned to the client (`T1`, `D2`, `P2`, `ER4`) carry `{ chain_id, safe_address, entry_point, module, op, sponsored, fee? }` — the server fills `op.paymasterAndData` from CDP and sets `sponsored: true` when the action is inside policy; otherwise `sponsored: false` with `fee: { eth, eur }` paid from the account's own Ether. Two new codes cover the edges: `SPONSORSHIP_REFUSED` (409, `reason: cap_reached|policy_mismatch`) and `INSUFFICIENT_FEE_BALANCE` (409, self-paid action without enough Ether) — both explicit, never a silent failure. **Phase 0 verification items**: confirm CDP actually supports EntryPoint v0.7 on both Base and Base Sepolia; confirm how the ZK Email relayer's own on-chain submissions get paid (the relayer operator funds them directly — a small ETH float on the relayer's own address if self-hosted — separate from the paymaster, which only sponsors the *account's* UserOperations, not the relayer's proof-submission transaction) against the actual module flow.
- **Clear signing of UserOperations (mobile's section 4.6, backend-relevant)**: the app decodes `Safe4337Module.executeUserOp(to, value, data, operation)` itself; `operation` must be `CALL` (or `MultiSendCallOnly` with every sub-call decoded the same way); targets are checked against the same pinned allowlist backing the on-chain address registry (property token contracts, supported stablecoins, the offering/escrow contracts, `VistaBloxWalletRegistry`, the Safe itself for owner changes, the email-recovery module for `cancelRecovery`) — anything else is refused, never blind-signed. Owner changes are rendered in plain language with the device's model, and the app independently recomputes a new owner's address from its public key before approving, refusing on any mismatch.
- **No on-chain guard for limits — decided by Damir (r7): the wallet itself enforces nothing.** Mobile-dev's owner-controlled Safe-guard proposal is explicitly not being built. VistaBlox's limits and holds apply only on the backend-relayed path; the public-bundler fallback is **intentionally unrestricted** — accepted as a deliberate trade-off of the zero-control design, not a gap left open to close later. Worth stating plainly in the threat model rather than leaving it implicit: anyone holding an owner key can, via the fallback, move funds with no VistaBlox-side limit at all, and that's the accepted cost of VistaBlox never being a gatekeeper.
- **ERC-3643 registration**: the Safe's address gets registered in the property token's identity registry (`VistaBloxProperty.sol`'s `_authorizedHolders`/`TRANSFER_AGENT_ROLE` mechanism — functionally ERC-3643-equivalent even though not literally the standard) at the same point KYC approval already happens today. Issuer-side agent-role recovery (`forceTransfer`) stays the last resort for property tokens specifically; it does not cover stablecoins (EURC), which have no such mechanism.
- **Audit-status deliverable — DevOps's tracking table is authoritative** (`devops-device-bound-auth.md` §10.6); this plan's Phase 0 owns closing the remaining "to verify" cells rather than duplicating the table. Verified so far: `zkemail/email-recovery` (Ackee, July 2024, commit `4e70316`: 27 findings, 0 critical, 2 high, 5 medium), `Safe4337Module v0.3.0` (tested and audited against EntryPoint v0.7). `Safe7579`'s audit status is no longer relevant to Phase 0's checklist given it's not part of the settled stack — flagged separately to Damir since dropping it departs from his own "ERC-4337 + ERC-7579" round-2 wording, pending his explicit confirmation. Still to verify: the ZK Email remediation report and the Zellic report's scope, **especially confirming the 2 high-severity findings from Ackee's audit are actually fixed in whatever commit gets pinned** (Damir's explicit emphasis, not a generic "check the report" item), the `Safe4337Module`/passkey-signer v0.2.x auditor names, the passkey signer's actual Base deployment, the DKIM registry/verifier's own audit status, and the relayer-plurality question above.
- **Mainnet gate — decided by Damir: no external audit budget.** Going to mainnet is gated on his own sign-off across four things, not a third-party audit of VistaBlox's own integration: (1) confirmation that zero custom on-chain code exists in the critical path (true by construction per "deploy nothing custom" above, but confirmed explicitly, not assumed); (2) the existing audit reports for every dependency read in full, with remediation verified — this plan's Phase 0 audit-status deliverable is exactly that work; (3) an internal review checklist (not yet written — a Phase 0 deliverable of its own, distinct from the audit-status table); (4) a Base Sepolia soak test exercising adversarial cases (replay, wrong device, revoked device, malformed owner-assertion, recovery-cancel timing, sponsorship-refusal handling), not just the happy path.

## Threat model / abuse cases per flow

| Flow | Abuse case | Mitigation |
|---|---|---|
| Enrollment | Attacker replays a captured `enrol/verify` request | Challenge is single-use (`auth.device_challenges` unique constraint + atomic consume), ~60s TTL |
| Enrollment | Attacker submits a software-only key claiming hardware backing | Android: certificate-chain verification against Google's published roots + revocation list, explicit hardware-backed flag check in the attestation extension. iOS: App Attest assertion is itself the hardware-backing proof; no software key can produce a valid one. |
| Enrollment | Attacker front-runs the challenge, submits their own key before the legitimate device does | `attestationChallenge`/`clientDataHash` (both derived from `binding = SHA-256(challenge ‖ "." ‖ bio_jkt)`) bind the specific challenge to the specific key being registered — a different key produces a verification failure, not a race the attacker can win by being first |
| Login | Attacker steals the device_id (not secret) and tries to log in from a different device | `device_id` alone verifies nothing; the signature must verify against the *stored* key, and the DPoP `jkt` on the request must match the device record — an attacker without the actual hardware key fails signature verification regardless of what device_id they send |
| Login | Enumeration (does this device_id/email exist) | `DEVICE_LOGIN_FAILED` is deliberately undifferentiated (except `DEVICE_CHALLENGE_EXPIRED`, which reveals nothing about the account); recovery `start` always returns `202` |
| Transaction signing | Confused-deputy: sign a request that isn't the one displayed | Field-by-field server-side comparison of the `tx` JWS claims against the stored request (`TX_FIELD_MISMATCH` on any difference), not just an opaque hash approval; client renders exactly what it will sign |
| Transaction signing | Malicious/misleading transaction description shown to the user | Clear signing requirement: the client decodes the proposed UserOperation *itself* and signs based on its own decode, refusing to sign on any disagreement with the displayed amount/destination; the server never supplies a human-readable description the client blindly trusts (this is the Bybit Feb-2025 failure mode named in the brief) |
| Transaction signing | Replay a previously-valid signed request | Challenge single-use + atomic `status` transition to `signed`/`submitted`/`included` on completion; re-submission hits `REQUEST_ALREADY_CONSUMED` |
| Transaction signing | Sign from a different device than the one that has an active session | Explicit cross-check: session's `dpop_jkt` and the JWS-signing device's `device_id` must resolve to the *same* device record (`TX_WRONG_DEVICE` otherwise) |
| Transaction signing | Device revoked mid-flight (between propose and sign) | Revocation (D3) cascades to cancel pending requests for that device (see Data model), and status is re-checked immediately before submission |
| Transaction signing | Client relays `signed_user_op` directly to a public bundler, bypassing VistaBlox's limits/holds | This is the explicit, accepted fallback (round 2) for when VistaBlox's own relay is unreachable 7+ days — not something this design tries to prevent. The Safe's own threshold-1 authorization is the only guarantee left on that path; VistaBlox's request-matching/limits/holds only apply on the backend-mediated path, which stays the default. Documented as a residual, accepted trade-off, not a gap to close — see "Wallet architecture." |
| Wallet: owner authority | **Threshold 1 means any single enrolled device can authorize *any* Safe operation alone** — sign a transfer, add a new owner, or remove every other device — with no on-chain requirement for a second signer. In the normal backend-mediated path this is constrained by VistaBlox's own purpose-scoped JWS/challenge layer (a device can only do what its signed request says, and only against the exact request the backend proposed); the raw on-chain capability is broader than what the backend ever lets a device exercise in practice. A single compromised device is therefore a full account compromise **as long as the backend-mediated path is used** — worth stating plainly since it's a structural property of "VistaBlox has zero control," not a bug to fix. |
| Wallet: pairing/revoke → on-chain mapping | A bug maps a `manage-device`-purpose approval to the wrong Safe `removeOwner` call, or an `approve-new-device` approval to the wrong `addOwner` call | `auth.wallet_owner_changes` records `target_bio_jkt` explicitly per row, tied 1:1 to the device/pairing record that authorized it; the UserOperation the backend constructs is built from that row, not re-derived ad hoc per call site — one construction path, testable in isolation from the JWS-verification logic itself |
| Wallet: ZK Email recovery | A relayer forges or replays a DKIM/ZK proof to rotate owners without the mailbox owner's involvement | The relayer only *submits* an already-valid proof to the on-chain verifier — it holds no key and can't forge a proof the verifier would accept; this is a property of the ZK Email module itself, which is exactly why its audit status is called out as its own deliverable (see "Wallet architecture") rather than assumed safe by this plan |
| Wallet: ZK Email recovery | Attacker who compromises the user's email attempts an unnoticed owner rotation | 7-day delay before the rotation takes effect, and any currently-enrolled device can cancel it during that window (`ER4`/`ER5`, owner-assertion purpose `cancel-recovery`) — the security event watcher (Observability) is what actually makes the cancel window usable in practice, since a silent 7-day timer nobody sees isn't a real mitigation |
| Wallet: single-device recovery | The account's only device is lost — there's no second device left to cancel a fraudulent email recovery during the 7-day window | Mailbox security, the 7-day delay, and the guardian-acceptance step (`W2`, confirmed once at onboarding) are the entire protection in this case — flagged plainly, not papered over: mobile-dev's own open item (an optional user-chosen second guardian, still with no VistaBlox key) is the candidate mitigation, not yet built (see Open questions) |
| Wallet: guardian mailbox coverage | The registered guardian mailbox's provider isn't in the DKIM registry (or is a private-relay address that can't send), so the customer can't complete `W2`'s acceptance step at all | Not resolved by this plan — mobile-dev flagged the same gap; a customer with no supported provider currently has no email-recovery path, which is worth surfacing before launch rather than discovering it from a support ticket (see Open questions) |
| Wallet: gas sponsorship refusal | The paymaster refuses to sponsor a legitimate action (cap reached, policy mismatch) at exactly the moment a customer needs to act (e.g. cancelling a fraudulent recovery) | `cancelRecovery()` is always sponsored, uncapped, specifically so this can't happen for the one action where it would matter most; everything else fails explicitly (`SPONSORSHIP_REFUSED`) rather than silently, and the self-paid fallback path (`INSUFFICIENT_FEE_BALANCE` otherwise) stays available |
| Wallet: recovery vs. KYC | Assuming KYC approval is what protects the wallet from a fraudulent recovery | It doesn't, structurally, under a zero-control design — the on-chain rotation completes after 7 days regardless of the KYC case's outcome; only a device-side cancel actually stops it. KYC still gates *auth*-side session access, but stating this distinction plainly here so it's never assumed to also gate wallet ownership — a mistake worth ruling out explicitly rather than leaving implicit. |
| Wallet: DKIM registry | The `UserOverrideableDKIMRegistry` the ZK Email module checks proofs against is an external dependency VistaBlox doesn't control — a compromise or misconfiguration there could accept a forged DKIM proof, or block a legitimate one | Named here as a real, external trust dependency rather than folded silently into "the module is audited" — the module's own audit doesn't cover the registry's operational security, which is DevOps's ongoing concern, not a one-time code review |
| Wallet: contract supply-chain | A wrong or swapped contract address gets configured for the Safe singleton/factory, `Safe4337Module`, the passkey signer, or the email-recovery module | The pinned `SAFE_*` address registry is checked against each artifact's `extcodehash` in CI — a mismatch fails the build, rather than the backend silently constructing UserOperations against unverified code at runtime |
| Wallet: owner-address spoofing | A device claims a different `owner_address` than the one its actual biometric public key derives | `owner_address` is server-recomputed from the stored public key before ever being used in a proposed operation, never trusted from the client's own claim (see "Wallet architecture") — a mismatch is a bug or an attempted spoof, either way rejected before any UserOperation is built |
| Wallet: clear-signing bypass | A UserOperation's `callData` targets a contract or method outside what the client's clear-signing decoder expects, and the client signs blind anyway | Mobile's decoder refuses anything outside the pinned target allowlist (property token, stablecoins, offering/escrow contracts, the wallet registry, the Safe itself for owner changes, the recovery module for cancellation) and anything but a plain `CALL` (with `MultiSendCallOnly` sub-calls decoded the same way) — this is a client-side control, but the backend's own proposed `user_op` should never construct anything outside that same allowlist in the first place, so the client's refusal is a backstop, not the only check |
| Wallet: ERC-3643 registry | The Safe's address isn't registered (or falls out of sync) in the property token's identity registry | Registration happens at the same point KYC approval already does today, not as a separate manual step; a desynced registry fails closed (the token contract itself rejects the transfer) rather than failing open, so this is a functional bug (transfers silently fail) rather than a security gap |
| Device approval (phone upgrade / pairing) | Attacker relay-phishes a victim into scanning a QR that pairs an attacker's device | E2's `pending_approval` path requires the new device to first pass Google/Apple sign-in to the *same account* (`PAIRING_ACCOUNT_MISMATCH` otherwise) plus full attestation before a pairing code is even issued, then requires the old device (P1) to display the new device's model/OS/location next to a 6-digit code the user compares out-of-band — not a bare "scan to approve". **No hold after a successful pairing — decided by Damir (r7)**, closing this plan's earlier-recorded 24h-hold alternative. If a relay-phishing attempt succeeds anyway, the newly-added device is immediately fully capable — the code-comparison/account-match checks above are the entire mitigation for this scenario, not a hold as a backstop. |
| Device approval (phone upgrade) | Attacker with a stolen *unlocked* old device approves an attacker-controlled new device | Same biometric-gated owner-assertion requirement applies to the old device's `approve-new-device` action (P2/P3, section 3.3) as to any other purpose — an unlocked phone alone isn't sufficient, the biometric still gates the key |
| Device management | A stolen bearer token/session alone is used to remove the owner's legitimate device | D2/D3 requires its own fresh owner-assertion via a dedicated challenge (purpose `manage-device`), not just an active session |
| Same-device re-enrolment | An attacker who knows the device passcode (shoulder-surfed, coerced) enrols their own face onto the phone | The KYC selfie (RE1/RE2) is **mandatory on every re-enrolment, not conditional** — Damir's explicit reasoning: a thief with the passcode can pass a biometric-enrolment prompt and usually finds Google already signed in on the phone, so the selfie face-match is the one step a thief who only has the device and its passcode cannot pass. With a second device, that device co-signs the on-chain `swapOwner` immediately (`next_step: "device_approval"`); with none, it routes through the 7-day email-recovery path (`next_step: "email_recovery"`), since there's no second owner to co-sign. |
| Recovery | Phishing a recovery link to a device the victim doesn't control | RC1 requires a DPoP proof (binds the case to that device's `jkt`); RC2 requires a DPoP proof whose `jkt` matches (`RECOVERY_WRONG_DEVICE` otherwise); token lives only in the link fragment (never server logs/`Referer`); explicit "not this device? don't continue" wording in the email; `ER4`/`ER5` kill switch from an old, still-trusted device cancels the linked wallet-recovery request and the account-recovery case together |
| Recovery | Deepfake/injected face during the recovery KYC re-check | Native in-app capture only (no web link), active liveness with injection detection in the Didit workflow, App Attest/Play Integrity on the recovering device |
| Recovery | KYC-credit exhaustion / inbox-flooding a victim | Didit session created only at RC2, after the email link is used, not at RC1 |
| Recovery | Weak/auto-approved match lets an impersonator through | Auto-approve only on a strong face-match score; anything weaker goes to `manual_review`, the existing dual-review staff flow |
| Enrollment/login | Devices without Google Play Services (e.g. Huawei) can't produce a Play Integrity verdict | **Decided: blocked at launch.** Enrolment is rejected with `DEVICE_UNSUPPORTED` (section 3.5, settled) rather than a generic attestation failure. Key-attestation-only enrolment with stricter limits is a later option, not built now. |
| Enrollment | A device with only weak (Class 2) biometric hardware attempts enrolment | Android: the key-attestation extension's reported user-auth class is checked, not just presence of *some* biometric; iOS: relies on App Attest proving the genuine app set `.biometryCurrentSet`, same platform asymmetry as elsewhere in this plan. Rejected outright — round 2 removed the fallback class this device class would otherwise have used. |
| All device-bound flows | A better-auth/library upgrade silently changes how signed claims are merged or verified | Direct-dispatch regression tests (the `dispatchAuthEndpoint` pattern from #49) for any new before/after hook this introduces, not just handler-level unit tests |

## Test strategy

- **Unit**: JWS verification per purpose (accept/reject matrix mirroring `dpop-proof-verifier.test.ts`'s structure — malformed header, wrong `alg`, wrong `typ`, private-key-material-present, wrong purpose, expired `iat`, tampered claim after signing).
- **Negative/security-specific** (each maps to a Threat model row above): replay a consumed challenge; purpose confusion (a valid `login` JWS presented where `tx` is expected); wrong device (valid signature, wrong `device_id`/`jkt` pairing); revoked device attempting login/sign; invalidated biometric key (simulated `KeyPermanentlyInvalidatedException`-equivalent server-side: a login attempt referencing a `device_id` whose key was superseded by re-enrollment); attestation failure (tampered cert chain, wrong `attestationChallenge`, non-hardware-backed key); relay-phishing recovery attempt (redemption from a different `jkt` than the one that started it).
- **Integration**: attestation verification against real Android/iOS attestation fixtures (request test fixtures from mobile-dev once their platform code exists — this can't be meaningfully faked the way DPoP proofs could be self-signed in this session's own tests, since attestation chains terminate in vendor-controlled roots).
- **Dispatch-level**: any new better-auth plugin hooks get the same `dispatchAuthEndpoint`-based regression coverage introduced in #49, not just handler-level tests, given that pattern is exactly what caught the bearer/passkey-cookie bug a handler-level test alone would have missed.
- **End-to-end on staging**: same validation loop used for DPoP — a real device test per phase before widening rollout, logs read for the corresponding audit events, not just an outcome-based pass.
- **Recovery email on staging**: staging keeps `maildev` (DevOps decision, section "Configuration and secrets"), and since the recovery link is a verified App Link it works from any browser — the test is to open maildev's web UI from the phone itself over the LAN and tap the link there, no staging ESP needed.

## Observability, audit, feature flags, rollout

- Every new endpoint gets an audit event through the existing `AuthAuditSink`, following the DPoP precedent from this session: log enough to reconstruct what happened (device_id, purpose, outcome, account_id) and never the signature, the raw challenge, or key material.
- Structured logs (`logger.info`/`.warn`, matching the `dpopLogger` pattern from #45): info on successful enroll/login/sign, warn on any rejection with its specific error code, matching the "why did this session land unbound" observability lesson from the DPoP rollout — the first version of that shipped without server-side visibility into binds/rejections and needed a follow-up fix once real device tests started surfacing silent failures.
- Feature flags: served by `GET /v1/app/config` (C1) — `device_auth`, `device_enrolment_required`, `passkey_login`, `signing_requests`, `recovery_v2`, plus `min_app_version` — each independently toggleable, so disabling `signing_requests` doesn't also have to disable `device_auth` if only one misbehaves in production.
- Rollout: staged the same way as DPoP's `DPOP_PHASE1_CUTOVER_AT` — an explicit, operator-set cutover marker per phase, not an implicit "whenever the code ships" behavior change, and each one documented in `.env.example` with the same "why this is pinned, what breaks if it moves" rationale that var got.
- **Push and email (Damir's decision 12)**: every push stays content-free (FCM/APNs, D4) as already specified in section 3. Security-relevant events additionally go out by email, not push-only: new device paired or enrolled, re-enrolment, device revoked, recovery started, recovery completed, recovery cancelled. No SMS for now. This reuses the existing SMTP-backed email-sending path (`BetterAuthCustomerAccountAdministrator`) rather than a new channel — one email template per event, each auditable the same way as the push/audit events above.
- **SMTP (Damir's decision 13, DevOps-owned, blocks Phase 3)**: the existing `SMTP_HOST=smtp.example.com` placeholder (5f) must be replaced with a real, production-grade sender before Phase 3 ships, and Damir's requirement is explicit: SPF, DKIM, and DMARC `p=reject` must all be in place, because recovery emails are exactly the template a phisher would clone. Not this plan's to build, but it's a hard Phase 3 blocker, not just a nice-to-have.
- **On-chain security event watcher (round 2, DevOps)**: a backend service watching the Safe's own events — `RecoveryRequested`/`RecoveryCompleted` from the ZK Email module, owner changes (`AddedOwner`/`RemovedOwner`/`ChangedThreshold`), module changes, fallback-handler changes, and unusually large outflows. Each one triggers an *immediate* push to every enrolled device plus a security email, on top of (not instead of) the existing `AuthAuditSink` logging — this is specifically the detection layer that makes the device-cancel window in "Wallet architecture" actually usable, since a user can't cancel a rotation they don't know is happening. Not gated on chain-indexer infrastructure existing elsewhere in this codebase (there isn't any yet) — a small, purpose-built watcher for this event set, not a general-purpose indexer.

## Implementation follow-ups (backend, not wire-contract)

Small, deliberately-deferred items surfaced during the #58 security review of the step-1 enrolment/login backend (vistablox-api#54/#58) — none of these change section 3's wire contract, and none block the Xiaomi device test.

- **Orphaned device row on session-creation failure**: if `internalAdapter.createSession` fails or returns `null` right after `EnrolDeviceService`/`LoginDeviceService` has already inserted/looked up a device row, that row is left behind with no session ever issued. Needs a `DeviceRepository` delete path (or a DB transaction wrapping both steps) to clean up on that specific failure. Not built as of #58 — the failure mode is rare (a session-creation failure immediately after a successful device insert) and cleanup can wait for a dedicated small PR.
- **`attestation_metadata` stores the full raw certificate chain** (`Device.attestationMetadata`, currently `{ keyAttestationChain: string[] }` verbatim) rather than a reference or a small summary (e.g. serials, thumbprints, security level). Fine for step 1's volume, but worth revisiting before this table sees production traffic, both for storage size and because the raw chain isn't something a support/ops view should need to render in full.
