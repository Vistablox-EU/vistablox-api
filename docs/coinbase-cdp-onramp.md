# Coinbase CDP onramp

This is the buy-side (`EUR -> EURC`) REST surface that backs reservation funding (`AD-255`). It is a distinct Coinbase CDP capability from the on-device wallet-key tooling `AD-246` names — this client never touches signing key material, only the onramp/offramp REST API documented at `docs.cdp.coinbase.com/onramp`.

## Runtime flow

1. `CreateReservationService` creates the reservation row and its first `money.money_events` row inside one transaction (`AD-146`; see [`investor-offering.md`](investor-offering.md#reservation-creation)).
2. It then calls `POST /onramp/v1/token` with the investor's already-registered wallet address (stored lowercase; the client sends Coinbase its EIP-55 checksum spelling, and passes anything that is not a valid address through unchanged), synchronously in the request path, and records `eurc_purchase_pending`.
3. The response is turned into a hosted purchase URL (`https://pay.coinbase.com/buy/select-asset?sessionToken=...&partnerUserRef=...&redirectUrl=...`) and returned to the client. The investor picks their own payment method inside Coinbase's hosted UI — VistaBlox never collects or stores one, which is load-bearing for `AD-254`'s non-custody position (the purchase must be investor-initiated, not something VistaBlox performs on their behalf).
4. `partnerUserRef` is the reservation ID, not the account ID, so a later `GET /onramp/v1/buy/user/{partnerUserRef}/transactions` call resolves unambiguously to one reservation even if an account has reserved more than once over time.

Advancing `capital_state` past `eurc_purchase_pending` has two triggers that share one code path (AD-289, decided 2026-11-17: webhook first, then an authoritative CDP re-fetch, with the poll as the backstop):

- **Webhook (fast path).** CDP sends signed onramp transaction events (`onramp.transaction.created`, `.updated`, `.success`, `.failed`) to `POST /webhooks/coinbase-onramp` (see [Webhook](#webhook) below). The API verifies the signature, then in one transaction writes a minimised receipt and enqueues a `provider_events.coinbase_onramp_webhook` job carrying only the reservation ID, the event ID and the event type. The worker looks the reservation up in whatever stage it is in and re-runs the poll's own reconciliation for it.
- **Poll (backstop).** `case_timers.reservation_onramp_poll` (`PollOnrampTransactionsService`, run every minute by the worker process) still lists every `initiated` reservation awaiting its purchase and calls step 4's endpoint for each. It catches anything the webhook missed: a delivery that never arrived, a subscription that isn't configured, or an event that reached us before CDP's Transaction Status API reflected it. It is the only worker job so far that the worker skips registering entirely when its provider credentials aren't configured; every other scheduled job's dependencies are always present.

Both triggers call `PollOnrampTransactionsService.reconcileReservation`, which resolves the outcome from the full transaction list (following the page cursor, up to 10 pages) and records it through **one** method, `ReservationRepository.recordOnrampOutcome`. Under the reservation's `FOR UPDATE` row lock, the one `recordMoneyEvent` and `expireReservation` also take, it reads the stage and the latest money event and decides (`decideOnrampRecording`, `domain/onramp-outcome-recording.policy.ts`), in this order:

| Situation (checked in this order) | Result | Row written? |
| --- | --- | --- |
| This provider transaction in this `capital_state` is already recorded for the reservation, at any point in its history and in any stage | `duplicate` | no |
| The reservation is no longer `initiated` (lapsed, cancelled, or past funding) | `other_stage` | no money event; a success is listed as late evidence by the handler |
| The latest event is a funded state (`eurc_reserved`, `reconfirmation_pending`, `eurc_finalized`) | `already_funded` | no; never an unfunded event over funded money (#201), and no second funding either |
| The latest event is neither `eurc_purchase_pending` nor `purchase_failed` | `not_awaiting_purchase` | no |
| Otherwise | `recorded` | yes |

The dedupe is per provider transaction and state across the whole history, not just against the latest event, for two reasons: the poll keeps listing a `purchase_failed` reservation every minute and must not write the same `purchase_failed` row again each time, and after a retry puts the reservation back to `eurc_purchase_pending`, the earlier failed transaction (still in Coinbase's list) must not immediately fail the retry. There is deliberately no unique index behind it: `money_events` is append-only and the poll on `main` already wrote repeated `purchase_failed` rows before this change, so the lock is the guard. A duplicate webhook delivery, a webhook racing the minute poll, and a late `failed` after a recorded success therefore write nothing. The poller and the webhook job both honour the returned result: only `recorded` counts as acted on, and `other_stage` goes to `OtherStageOnrampOutcomeHandler` (`application/other-stage-onramp-outcome.ts`).

The row it writes is always the latest event of the reservation. `recorded_at` is the time the caller observed the outcome, read before it queued for the row lock, and the order the recorders win the lock in is not the order of those readings: two reconcilers can interleave with different views of Coinbase, and the API stamps the pending event with its own clock, which can run ahead of the worker's. Readers (the expiry sweep, the funded-progress sums) take the latest event by `recorded_at` as the state, so a funded event stored under a later-dated failed or pending one would be read as unfunded and the reservation lapsed with money on it. The stored `recorded_at` is therefore the caller's time, or one millisecond after the reservation's latest event when the caller's time is not later (`recordedAtAfterLatest`, in the same policy file): under the lock the order of the writes is the order of the history, which is what keeps the funded-over-unfunded guard an invariant rather than a check on whichever event happened to be sorted last. A row written this way can carry a time up to the clock skew later than the one observed; the observation time is not otherwise kept. `recordMoneyEvent` (the pending and failed events of `createReservation`, #201) still stores the caller's time as given.

That handler is the seam for the late-evidence path (#195, AD-288 as decided 2026-11-17), and in the worker it is `RecordOnrampLateEvidenceService` (`application/record-onramp-late-evidence.service.ts`). It receives the provider transaction id, tx hash, destination wallet, reservation id and stage, amount and asset, the state the outcome would have had, whether Coinbase reports the transaction as a success, and when it was observed. A success is written as one row of `money.onramp_late_evidence` (see [Late evidence](#late-evidence)); a failed attempt moved no money and is not. It is idempotent on the provider transaction id, since a webhook retry or both triggers can hand it the same transaction twice. No money event, no hold, no refund or reinstatement option (AD-243, AD-251, AD-260 step 9, AD-266). `LoggingOtherStageOnrampOutcomeHandler` (a warning with the ids and amounts, never the destination wallet) is only the default of a caller that wires none; the worker does not use it, and `tests/coinbase-onramp-webhook-wiring.test.ts` pins that the poller gets the evidence handler.

This does not extend the funding path. `RESERVATION_FUNDING_RAIL_ENABLED` stays `false` and the settlement bundle stays dormant (AD-285, decided 2026-11-17); this change only makes an outcome reach the recording method sooner, and exactly once. See [`investor-offering.md`](investor-offering.md#advancing-capital_state-the-onramp-transaction-poll) for the exact success/failed/still-pending resolution rule and the one race this pass deliberately leaves unresolved.

## Authentication

Every request carries a short-lived (120s) JWT bearer token, generated per request and verified directly against `@coinbase/cdp-sdk`'s own `auth/utils/jwt.ts` rather than assumed: EdDSA (a 64-byte base64 Ed25519 secret) or ES256 (a PEM EC private key) auto-detected from the configured secret's shape, header `{alg, kid: <key ID>, typ: "JWT", nonce}`, claims `{sub: <key ID>, iss: "cdp", aud: ["cdp_service"], uris: ["METHOD host/path"]}`. VistaBlox signs this itself with `jose` (already a transitive dependency via `better-auth`) rather than depending on the full `@coinbase/cdp-sdk` package, which pulls in an unrelated Solana/viem/axios dependency tree for the ~30 lines this actually needs.

## Configuration

Configure all three of these together, or leave all three empty to disable reservation funding (the funding rail then stays reported as `funding_rail_unavailable` regardless):

- `COINBASE_CDP_API_KEY_ID`
- `COINBASE_CDP_API_KEY_SECRET`
- `COINBASE_ONRAMP_REDIRECT_URL`

`COINBASE_ONRAMP_WEBHOOK_SECRET` is optional and separate: it enables the webhook route (see below). Leave it empty and the route is not mounted at all (requests get `404`), while the minute poll keeps working on its own. It requires `COINBASE_CDP_API_KEY_ID`, since the webhook only triggers a CDP re-fetch.

`COINBASE_CDP_API_BASE_URL` defaults to `https://api.developer.coinbase.com`. `COINBASE_CDP_PAY_HOSTED_URL` defaults to `https://pay.coinbase.com/buy/select-asset`. `COINBASE_ONRAMP_BLOCKCHAIN` defaults to `base`.

## Webhook

**What is established and what is assumed.** The signature scheme below follows CDP's webhook signature-verification page (`docs.cdp.coinbase.com/webhooks/verify-signatures`), which `CoinbaseOnrampWebhookVerifier`'s header comment cites and which the record's "CDP's standard webhook-verification flow" (`COINBASE_ONRAMP.md`, "Webhooks") refers to. Re-read on 2026-11-17 when this was rebuilt, that page gives: the `X-Webhook-Signature` header (`X-Hook0-Signature` deprecated, same values), `t`, `v0` (HMAC-SHA256 over `{t}.{rawBody}`), `h` and `v1`, a recommended maximum age of 5 minutes, an `X-Event-Id` header (and an `X-Event-Type` header), and an example that passes the subscription's secret to `createHmac` as a plain string. The page itself says nothing about decoding the secret, and its sample function compares only `v1` while its tip says `v0` is enough; this code checks `v0`. The record names the four event types, says `partnerUserRef` ties a delivery to its reservation, and says the payload carries the on-chain `txHash`. It does **not** give the payload's JSON keys, and neither does that page as read. So the body keys `eventType`, `partnerUserRef`, `transactionId` and `txHash` are **assumptions**, kept in one place and pinned by tests as assumptions. **No real signed delivery has been checked, here or on staging**, so the header, the secret handling and the keys are all still unverified against one. That check belongs to DevOps and needs the `COINBASE_*` variables (including `COINBASE_ONRAMP_WEBHOOK_SECRET`) passed through the `&app-environment` anchor of `docker-compose.staging.yml`, which does not carry any `COINBASE_*` variable today. A delivery whose shape differs from the assumptions is acknowledged with `200`, logged as a warning (no readable `eventType`, or no `partnerUserRef`), and left to the poll; nothing is lost, but the webhook does no work until the assumptions are confirmed.

**Subscribing.** Create one subscription per environment with the CDP CLI, pointing at `https://<api-host>/webhooks/coinbase-onramp` and listing the four `onramp.transaction.*` event types (`cdp data webhooks subscriptions create`). The response's `metadata.secret` is the value for `COINBASE_ONRAMP_WEBHOOK_SECRET`. The API must also have the CDP client configured; without it the route stays unmounted even when the secret is set.

The route is `/webhooks/coinbase-onramp`, next to `/webhooks/didit`, not under AD-066's `/provider/v1`; that divergence is recorded once in the design record's conflict register, not here.

**Verification** (`CoinbaseOnrampWebhookVerifier`):

- The route is mounted with `express.raw()` ahead of the app-wide JSON parser, so the HMAC is computed over the exact bytes CDP sent (capped at 256 KB).
- The signature header is `X-Webhook-Signature: t=<unix seconds>,v0=<hex>,...` (`X-Hook0-Signature` is accepted as CDP's deprecated name for the same value). Only `v0` is checked: `HMAC-SHA256(secret, "<t>.<raw body>")`, compared in constant time. Any other scheme in the header is ignored.
- `t` must be within 5 minutes of the server clock, in either direction, which is CDP's recommended maximum age and bounds replay of a captured delivery.
- A missing, malformed, stale or mismatched signature gets `401` with code `offering.coinbase_webhook_invalid`. Nothing else is ever rejected: a verified delivery always gets `200 {"received": true}`.

**What the body is trusted for.** Only the event type and the ids. Status, amounts, wallet address and the user's country are never taken from the body: the worker re-fetches the reservation's transactions from CDP, exactly as the poll does. A verified delivery that is not JSON, has no `eventType`, is not an `onramp.transaction.*` event, or whose `partnerUserRef` is not shaped like a reservation ID is acknowledged with `200` and not recorded or enqueued (an unreadable payload, or an `onramp.transaction.*` event with no reservation reference, is logged as a warning, since a renamed key would look exactly like that; an event type we do not act on is logged at info). Neither the body nor any PII in it (`walletAddress`, `country`, `userId`) is logged, stored or put in the job payload.

**Receipt (AD-289, decided 2026-11-17).** Each recognised delivery is persisted as a minimised receipt in `money.onramp_webhook_receipts`: event id, event type, Coinbase transaction id, `txHash`, `partnerUserRef` and `received_at`; never the body, the signature or a secret. The table is append-only (a trigger rejects every `UPDATE` and `DELETE`, as on `money_events`), unique on the event id, and written in the same transaction that enqueues the job (`enqueueTransactionalJob`), so a receipt without its job, or a job without its receipt, cannot exist. The event id is the `X-Event-Id` header (named by CDP's verification page), or, when it is missing, `body-sha256:<digest of the exact signed body>`, so a redelivery of identical bytes is still recognised. A redelivery of an event id already on file is acknowledged with `200` and does nothing: no second receipt, no second job. The alternative, keeping the receipt only in the job payload, was rejected: a pg-boss job row is archived and deleted by retention, so it is neither durable evidence nor a duplicate guard that outlives the job. Retention of the receipts is open, and needs its own migration once decided.

**Processing.** `ReceiveCoinbaseOnrampWebhookService` writes the receipt and enqueues `provider_events.coinbase_onramp_webhook` (event-job retry profile, dead-lettered after its last retry; owner `payments`, tier `tier_1` in `job-ownership.ts`). The worker's `ReconcileOnrampWebhookService` looks the reservation up in any stage, then calls `reconcileReservation`; its log line reports `ignored` (a reservation this database does not know), `unresolved` (Coinbase shows nothing concluded yet) or `resolved`, with the recording result (`recorded`, `duplicate`, `already_funded`, `not_awaiting_purchase`, `other_stage`). An `onramp.transaction.success` or `.failed` event that finds nothing concluded for a reservation that has already left `initiated` throws, so pg-boss retries it: the poll only covers `initiated` reservations, so a retry is the only way that evidence still reaches `other_stage`. The consumer is registered only when the worker has a CDP client; the queue itself is always created, so a send never fails against a missing queue.

## Late evidence

A Coinbase success for a reservation that has already left `initiated` is not funding and not a refund case: the EURC is already in the investor's own wallet (AD-243), and AD-251, AD-260 step 9 and AD-266 rule out a refund and a revival. It is kept as an ops-visibility entry so staff know it happened (AD-288, decided 2026-11-17).

- **Where it comes from.** The recording method's `other_stage` result, handed over by the webhook job (the only trigger that reaches a lapsed or cancelled reservation, since the poll lists `initiated` ones only) or by the poll when a lapse lands between its list and its lock.
- **What is stored.** `money.onramp_late_evidence`, unique on the provider transaction id: provider transaction id, `txHash`, destination wallet, reservation id and the stage it was in, amount and asset, state, `observed_at`, `reviewed_at` (null until staff mark it). The wallet is a public address linkable to an investor: staff see it in the list, and it is never put in a log line, an alert or an audit row. A row is immutable except for the one-time `reviewed_at`.
- **What staff do.** List it and mark it reviewed (`/internal/v1/offerings/onramp-late-evidence`, see [`investor-offering.md`](investor-offering.md#late-payments)). Nothing else.
- **The alert.** `offering.onramp_late_evidence_unreviewed`, `severity: warn`, raised hourly while any entry is unreviewed (level-triggered, counts and ids only).
- **Retries.** If the write fails, the handler throws: the webhook job is retried by pg-boss, and the poll counts the reservation as failed. A lapsed reservation is not in the poll's list, so for it the webhook retry is the only route; the write is idempotent, so a retry cannot duplicate.
- **Not verified here.** No real signed delivery has been checked on staging (it needs the `COINBASE_*` variables in the `&app-environment` anchor of `docker-compose.staging.yml`); the payload key names are assumptions (see [Webhook](#webhook)). Until DevOps checks one, treat the webhook-driven part of this path as untested against Coinbase.

## Data boundary

`listBuyTransactions` normalizes Coinbase's `OnrampTransaction` response down to what `capital_state` advancement actually needs (transaction ID, status, wallet address, purchase/payment amounts, tx hash, timestamps); fields like `user_id` and `end_partner_name` are read by nothing in this codebase and are dropped rather than persisted or logged.

## Errors and operator alerts

The client classifies every CDP failure by HTTP status and never reads or logs the response body.

| Upstream result | API error | Retry? | Operator signal |
| --- | --- | --- | --- |
| 5xx, 429, 408, network failure, timeout | `offering.coinbase_provider_unavailable` (503) | Yes, with backoff | None (transient) |
| 401, 403 | `offering.coinbase_provider_auth_rejected` (500) | No | `event: coinbase_cdp.auth_rejected`, `severity: error` |
| Any other 4xx | `offering.coinbase_provider_request_rejected` (422) | No, not unchanged | `event: coinbase_cdp.request_rejected`, `severity: warn` |
| Unusable `COINBASE_CDP_API_KEY_SECRET` (no request sent) | `offering.coinbase_provider_key_invalid` (500) | No | `event: coinbase_cdp.key_invalid`, `severity: error` |
| A purchase succeeds after its reservation left `initiated` (webhook job, or the poll) | None: no request fails; an entry is written | No | `event: offering.onramp_late_evidence_unreviewed`, `severity: warn`, hourly while an entry is unreviewed (see [Late evidence](#late-evidence)) |

Alert lines follow the wallet-registry convention: a structured pino line with a stable dotted `event`, a `severity` (`error` pages, `warn` opens a ticket), and snake_case fields (`operation`, `http_status`). Alert rules key on `event` and `severity`, never on the message text. A 401/403 or invalid key means the API key is wrong, revoked, or lacks permissions; retrying will not help until the configuration is fixed.
