# Customer full-lockout account recovery

This implements `ACCOUNT_RECOVERY_POLICY.md`'s full-lockout path for the customer (investor/owner-applicant) population — what happens when a financially active account loses access to both linked login methods at once. Ordinary recovery (one method lost, the other still works; either provider's own password reset or Google recovery) needs no VistaBlox code at all and stays untouched. Staff/partner recovery is a separate, already-built, single-admin flow (`/internal/v1/auth/staff-accounts/:account_id/recovery`) — this document only covers the customer case, which the policy deliberately makes higher-friction: dual review, a fresh identity re-verification, and a cooldown after access returns.

## Runtime flow

1. The customer contacts support out of band (email, phone) — there is no self-service intake endpoint, since by definition this customer cannot authenticate. An `admin_operations` staff member, WebAuthn-verified, opens the case: `POST /internal/v1/account-recovery-cases`. This revokes every existing session for the account first (`context.internalAdapter.deleteUserSessions`, the same better-auth primitive staff recovery already uses), then creates the `account_recovery_cases` row and moves the account to `recovery_review` — a status `require-authentication.ts` already blocks every authenticated request against, so nothing further needs to check it explicitly.
2. Staff creates a fresh Didit verification session tied to the case (`POST /internal/v1/account-recovery-cases/:case_id/didit-sessions`), using the same baseline KYC workflow — re-proving a live human with a valid ID is the same check, not a new provider configuration — and relays the hosted verification URL to the customer through the same out-of-band channel.
3. A reviewer reads `GET /internal/v1/account-recovery-cases/:case_id`: the case's current state, the Didit session's live status (re-queried from Didit on every read, the same re-query pattern `ReconcileStuckOpenSessionsService` uses, not trusted from a webhook), and a safe view of corroboration facts already known to VistaBlox (last deposit amount/date, last reservation amount/date, last login method/date) for the reviewer to compare against what the customer states. The system does not attempt to automatically match customer-supplied answers against these — the policy's own "without revealing which answer failed" instruction only makes sense as a human judgment call.
4. That reviewer records their primary review (`POST /internal/v1/account-recovery-cases/:case_id/primary-review`, naming which corroboration category they used) — rejected unless a Didit session is already on file.
5. A **different** reviewer decides (`POST /internal/v1/account-recovery-cases/:case_id/decision`, `approved` or `rejected` with a reason). The same reviewer cannot decide their own primary review; this is enforced atomically in the repository's `UPDATE ... WHERE reviewed_by_primary IS NOT NULL AND reviewed_by_primary != $reviewer`, not just checked in the service layer. Rejection is terminal for that case and leaves the account in `recovery_review` — no further restriction is added, and no access is granted; a human follows up out of band.
6. Once approved, staff completes it (`POST /internal/v1/account-recovery-cases/:case_id/complete`): this sends the customer a password-reset-style link via better-auth's own `requestPasswordReset` (the same mechanism staff recovery uses), which lets them establish a new session bound to their existing `account_id` without needing one already. This is why full-lockout recovery is only reachable for a financially active account in the first place — `AD-015`'s Recovery Readiness Requirement already guarantees email/password was one of the two linked methods before the account could ever invest.
7. The account moves back to `active` immediately — the customer is not locked out of ordinary browsing for another three days after finally regaining access — but a 72-hour cooldown (`cooldownEndsAt` on the case) blocks new reservations specifically (`recovery_cooldown_active`, wired into `reservation-eligibility.policy.ts` alongside every other reservation blocker). The customer still needs to re-link their second login method through the ordinary, already-existing linking flow before `login_methods_incomplete` clears and investing is possible again — nothing new was built for that half, since the existing gate already requires it.

## What the 72-hour cooldown does and does not cover

`ACCOUNT_RECOVERY_POLICY.md`'s Restricted Recovery State freezes five things: new investments/deposits, login-method changes, payout-destination changes, redemption/cash-out, and other sensitive actions. Only the first is enforced here:

- **New investments and deposits**: enforced — `recovery_cooldown_active` blocks `POST /v1/offerings/:offering_id/reservations` for the cooldown's duration.
- **Login-method changes**: not enforced. Better Auth's own account-linking endpoints handle this directly; this codebase has no VistaBlox-side gate in front of them to extend (linking is otherwise ungated once a session exists, cooldown or not). Closing this would mean building policy in front of better-auth's linking flow specifically for this case — out of scope here.
- **Payout-destination changes and redemption/cash-out**: not applicable — neither has any endpoint in this codebase yet (`AD-252`/payouts remain schema-only, confirmed by direct inspection).

## Data boundary

The same minimization discipline as KYC applies. The case table (`account_recovery_cases`) stores only the provider reference, the two reviewers' account IDs, status, and timestamps — not the corroboration category used, the reviewers' reasoning, or the decision rationale, all of which go to `audit.audit_log` instead (matching the policy's own Audit Trail Requirements list, which frames these as audit fields, not case-record fields). Corroboration facts are read live from existing operational data (reservations, money events, sessions) at review time and never separately persisted for this purpose.

## Follow-on work

- **Alerting** on a recovery case sitting open too long is not built, the same gap named for stuck-session reconciliation (`docs/didit-kyc.md`) — `AD-089`'s alert scoping does not cover this either.
- **Login-method-change freezing during the cooldown** — see above; would need a new policy gate in front of better-auth's own linking endpoints, which nothing in this codebase currently wraps.
- A customer whose *only* login method was ever Google (never set a password) has no path through `sendRecoveryCompletionEmail` as built — not reachable for a financially active account per `AD-015`, but worth naming if this flow is ever extended to non-financially-active accounts.
